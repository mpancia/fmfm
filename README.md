# FORMALFRED

A generative sequencer for the M-VAVE FM-1 pocket synth, with its sequencing logic proved in Lean 4 (Vibecheck
hackathon). Alfred the butler is the mascot.

**Site:** https://mpancia.github.io/fmfm/ has the web installer and the browser simulator. It is rebuilt from `main`
by `.github/workflows/site.yml` (`tools/make_site.py` assembles `site/` + `build/web` + the package).
See `docs/FM1.md` for research, hardware facts and flash safety.

```
make install && make run
```

Then open http://localhost:8000/ and click **Power on**. Four lanes start playing at once.

The panel is menu driven, in the manner of Mutable Dreams. Four buttons pick a group of pages, and pressing the
same button again moves to the group's next page. The four knobs set the four values shown on screen.

| Group | Pages (knobs 1 to 4) |
|---|---|
| HOME | overview of the four lanes: hits, steps, speed, chance |
| SEQ | RHYTHM: hits, steps, speed, chance, with the bar drawn as a circle (the hits joined, the current step bright). FEEL: the rhythm source (Euclid, rotate with accents, cellular automaton, ratchet) and its knobs. NOTES: the note source (random, walk, up, down, bounce, loop, turing, step, markov, grammar, chord) and its knobs, range. RANGE: scale, low note, chord follow. See `docs/SEQUENCERS.md` |
| EDIT | SOUND: shape, timbre, colour, level. ENVELOPE: attack, release, envelope-to-timbre. MIX: the four lane levels. PAN: the four lanes left to right (equal power: `mix_pan_equal_power`) |
| GLO | HARMONY: key, scale lock, chord progression, bars per chord. SYSTEM: tempo, keys octave, LOOK (seven looks; CATALOGUE, the site's paper and ink, is the default), SWING (0 to 100: the first eighth of each pair stretched, the second shortened, the pair kept exact: `swing_keeps_time`). MIDI: in and out channels, CLOCK (INT, or EXT: the lanes step on an incoming MIDI clock, start and stop follow it, the tempo it implies is shown). BANKS: patch, save slot, DEMO (the demo songs), AUTO (the device performs on its own: the demo songs in turn, 32 bars each, a lane varied every 8 bars; PLAY stopping ends it) |

| Control | Does |
|---|---|
| SELECT | choose a lane (in the browser: the sound or patch group) |
| PRESETS | open the browser and scroll: sounds (199) in EDIT, patches (128 factory, 8 user) elsewhere, grouped as ALL, DEMOS, SONGS, the moods and USER (SELECT picks the group). Sounds are grouped by engine (analog, filter, voice, FM, physical, percussion, wavetable, noise) or by type (tone, pluck, pad, drum); ALGO switches the grouping while the browser is open, SELECT picks the group |
| ALGORITHM | tempo (in the sound browser: the grouping) |
| PLAY | start or stop the clock (stopping silences every lane) |
| SEL | mute the chosen lane |
| REC | roll a new variation of the chosen lane |
| SAVE | keep the patch in the slot chosen on GLO > BANKS |
| ARP | the arpeggiator page: the keys you hold play one at a time in step with the clock, on the chosen lane's sound (MODE up, down, up-down, random, as played, or off; RATE; OCTAVES; GATE). ARP again on that page latches the notes so you can let go; PLAY stopping lets them go too |
| keys, OCT- OCT+ | play the chosen lane's sound by hand |

The FX button opens the sends: REVERB (Clouds' reverb, ported to Lean: SEND of the chosen lane, DECAY, BRIGHT,
RETURN), then DELAY (a tempo-synced ping-pong echo on the same send: TIME as a note value, FEEDBK, TONE, RETURN). See
`docs/FX.md`.

Note algorithms (SEQ > NOTES), per lane: RANDOM, WALK (random steps of up to AMOUNT notes), UP, DOWN, BOUNCE, and
LOOP (a memory of AMOUNT notes that replays, with MUTATE percent chance of replacing a note each time).
Chord progressions (GLO > HARMONY, written as scale degrees so 1-4-5-1 is I IV V in a major key and i iv v in a
minor one) change the chord every bar or more; a lane follows them in SEQ > RANGE: 7TH keeps the chord's seventh (the first, third, fifth and seventh note of the key's scale from the chord root),
TRIAD its triad; both are built from the key's scale, so a lane following chords never leaves the key
(`harmony_follow_in_key`). COMPL plays the notes outside the key's scale instead (the black keys to its white),
which have the scale's own interval content, each interval the same number of times fewer
(`harmony_complement_interval_content`, Babbitt's hexachord theorem in general form).
The last three progressions are walks on the Tonnetz (`Firmware/Tonnetz.lean`): the chord moves by the
neo-Riemannian P, L and R, each keeping two of the triad's notes and moving one, in a repeated word: WALK LR
visits all 24 major and minor triads in turn and comes back, WALK PL is a hexatonic cycle of six, WALK PR an
octatonic cycle of eight; a lane with 7TH or TRIAD plays the walk's triad, so the key is left one note at a time.
`Proofs/Tonnetz.lean` is the group theory: the moves generate the dihedral group of order 24, acting simply
transitively on the triads and commuting with every transposition and inversion.

Each lane is a clock divider driving a Euclidean rhythm; every hit picks a random note in the lane's range and
snaps it to the scale. That logic is Lean, and so are the sound engines, the effects and the patch format; the
section "What is proved" below says what is promised about each.

The sound is Mutable Instruments' Braids, all 48 of its oscillator shapes, compiled from its own source
(`voices/`). `make audit` checks every factory sound.

The simulator runs the real firmware app (`fw/firmware/src/dinghy.c`) compiled to WebAssembly, with the FM-1's
screen, keys, buttons, knobs, audio and (in Chrome/Edge) MIDI in. No FM-1 needed. See `docs/SIMULATOR.md`.

<details><summary><b>The sequencer</b>: 80 theorems</summary>

The four lanes and what they play. Over a whole performance no note is left sounding, the clocks never drift apart,
rhythms have exactly the hits asked for, and every note is in the scale and the range.

| Theorem | Says | Protects against |
|---|---|---|
| `lane_make_valid` | Whatever settings are asked for, `make` gives a consistent lane. | bad numbers from the screen or a saved file cannot put a lane into a state the rest of the code does not expect. |
| `lane_reconfigure_valid` | `reconfigure` keeps a consistent lane consistent, even for nonsense settings. | turning a knob mid-song can never leave the lane with a position or timer out of range. |
| `lane_set_notes_valid` | Changing the note algorithm keeps a consistent lane consistent, whatever numbers are given. | switching a lane from random to loop in the middle of a song cannot leave its loop position outside the loop. |
| `lane_tick_valid` | A tick keeps a consistent lane consistent. | however long the music runs, the counters stay in range, the note memory stays sound, and the sounding note and its timer stay in step. |
| `lane_gate_end_stops_note` | When a sounding note's gate runs out, the tick reports it as stopped. | no note stays on after its gate, so no stuck notes. |
| `lane_new_note_stops_old` | A tick that starts a note also stops the one sounding before it. | a lane never has two notes on at once, so every note-on has exactly one note-off. |
| `lane_note_only_on_hit` | A note starts only on a step the rhythm marks as a hit (the step the note belongs to: for a ratchet's sub-hit, the step that just pulsed). | the rhythm's pattern is respected, whichever rhythm source makes it; a rest never plays, whatever the note algorithm or the play chance say. |
| `lane_note_in_scale` | A note a tick starts is a valid MIDI note and is in the lane's scale. | the lane can never play a note the voices reject, or a note outside the key you chose, whichever note algorithm it uses. |
| `lane_silence_valid` | Silencing a consistent lane leaves it consistent. | stopping the clock cannot leave the lane with a timer and no note, or a note and no timer. |
| `lane_silence_stops_note` | Silencing reports the sounding note as stopped and leaves nothing sounding. | pressing stop never leaves a note hanging. |
| `lane_reconfigure_self` | Applying a lane's own settings back to it changes nothing, for a consistent lane whose settings are the ones the knobs can reach (steps up to 32, speed up to 96 ticks, algorithm 0 to 10, mutation up to 100 percent, a rhythm source in range with a live automaton row that fits the bar, the step sequencer's cursor inside its loop) and whose gate is the one its speed gives. | saving a patch and loading it again, or redrawing a knob at its current value, cannot alter the music by a tick: the lane is exactly where it was. |
| `lane_set_rhythm_valid` | Changing the rhythm source keeps a consistent lane consistent, whatever numbers are given. | switching from Euclid to the automaton or the ratchet mid-song touches nothing but the rhythm; counters, memory and the sounding note stay as they were. |
| `lane_learn_valid` | A key the player presses keeps a consistent lane consistent. | playing along, or programming the step sequencer, can never break the lane. |
| `lane_from_patch_keeps_feel` | A patch lane that fits gives a lane with exactly the rhythm source the patch holds: none of the clamps on the way (`Lane.make`, `Rhythm.make`) change a fitting value. | the FEEL settings a patch saves are the ones it plays back; what you hear after loading is what you heard before saving. |
| `run_every_note_on_has_a_note_off` | Every note a lane starts during a run is stopped: after any sequence of ticks and setting changes, the number of note-ons equals the number of note-offs plus the one note still sounding, which stopping the clock then reports as stopped (`lane_silence_stops_note`) and leaves nothing sounding. | this is the no-stuck-notes promise for a whole performance, not one tick: however long you play and whatever you turn, pressing stop leaves nothing sounding and nothing unaccounted for. |
| `run_clock_never_drifts` | After `n` ticks from a fresh lane, the clock stands at `(n / div) % steps`, whatever notes played. | the step position depends only on the tick count, so four lanes at different speeds stay in phase forever: nothing a note does can make a lane drift. |
| `run_bar_plays_every_hit` | A plain lane (the Euclidean source, play chance 100) plays exactly `hits` notes in a bar: over the `steps * div` ticks of a bar from a fresh lane, the trace has `hits` note-ons, for any settings at all (`make` holds them to what the knobs can produce). | the safety theorems say a lane never plays on a rest; this one says it does play on every hit. |
| `rhythm_automaton_row_fits` | One generation of the automaton stays inside the bar: the new row has no bit at or beyond `steps` (a bar has at most 32 steps). | the row is a `steps`-bit pattern however long the automaton runs; a hit can never appear on a step that does not exist, and the row stays the size the circle draws. |
| `rhythm_accent_only_on_hit` | An accent only falls on a hit. | accents shape the rhythm's hits; they can never add a note where the pattern has a rest. |
| `rhythm_rotate_keeps_hits` | Turning the bar (ROTATE) keeps the number of hits: a turned bar has exactly `hits` hits, like the plain one (`euclid_hit_count`). | ROTATE moves the pattern round the circle without adding or losing a note. |
| `rhythm_rule_zero_dies` | Rule 0 kills the row: after one generation nothing plays. | the automaton has a rule that is silence, and the reseed on a dead row is what brings the bar back. |
| `rhythm_rule_full_fills` | Rule 255 fills the bar: after one generation every step plays. | the other end of the rule knob is a wall of hits, so the circle shows the whole range from silence (rule 0) to everything (rule 255). |
| `rhythm_rule_204_freezes` | Rule 204 freezes the bar: a row that fits the bar comes back unchanged every generation. | there is a rule on which the automaton is exactly the Euclidean bar it was seeded with, so turning RULE from 204 is the way to make it move. |
| `swing_tick_in_range` | Every tick is between a third and five thirds of a straight tick, at every swing setting. | swing can never make a tick vanish (a zero-length tick would fire two steps at once) or stretch one past the next eighth. |
| `swing_keeps_time` | A tick of the first eighth and a tick of the second add up to exactly two straight ticks, so the twelve ticks of a pair of eighths take exactly 24 straight ticks, whatever the swing. | swing moves notes inside each pair of eighths and nothing else: a bar is as long as it was, the four lanes stay in phase with each other and with a MIDI clock, and `run_clock_never_drifts` still holds for the swung clock, tick for tick. |
| `swing_quarter_note_exact` | A quarter note under swing is exactly 24 straight ticks long, at every setting, and every tick inside it starts strictly after the one before (each is at least 3334). | swing is a feel, not a tempo change: a quarter note, a bar and a song take the time the TEMPO knob says, a MIDI clock sent out would stay in step with one received, and no two ticks can fall together. |
| `divider_pulse_count` | A divide-by-`div` counter that starts at 0 and gets `ticks` ticks gives exactly `ticks / div` pulses. | a divide-by-4 clock never drops or doubles a beat, however long it runs. |
| `divider_count_bounded` | The count never reaches `div`: it always stays between 0 and `div - 1`. | the counter is a small number for good, so it can never grow into a big number the chip's Lean runtime cannot handle. |
| `euclid_hit_count` | A bar of `steps` steps with `hits` hits (`hits ≤ steps`) plays exactly `hits` notes. | the pattern has the density you asked for, with no missing or extra notes. |
| `euclid_last_step_hits` | The last step of a bar is a hit whenever the bar has any hits. | the pattern always ends on a note, so the bar's last step (just before the circle comes round) is where every Euclidean rhythm lands; the ratchet's first sub-hit relies on it too. |
| `euclid_window_balanced` | Every window of `len` steps of a bar of `steps` steps with `hits` hits plays `len * hits / steps` notes or one more, wherever it starts, across the bar line included: the pattern is maximally even. | this is what "spread out" means and the reason the hits never bunch: 5 hits in 16 steps gives every 4 steps one or two notes, every 8 steps two or three, and any two stretches of the same length are within one note of each other. |
| `euclid_windows_within_one` | Two windows of the same length never differ by more than one note: a direct form of the balance. | whichever two bars, half-bars or beats you compare, the Euclidean pattern gives them the same number of notes or one apart; it has no busy and empty stretches. |
| `euclid_is_christoffel` | The firmware's pattern is the lower Christoffel word of slope `hits / steps` in Berstel's form: a step is a hit exactly when the multiples of `hits` wrap round modulo `steps` there (for `hits < steps`; `hits = steps` is every step). | it names what the sequencer plays: a Christoffel word, the discrete line from (0, 0) to (steps, hits), the same object as the maximally even scales, so everything known about those words (they are balanced, their conjugates are the Euclidean rhythms, their reversal is the upper word) is about these rhythms. |
| `euclid_bjorklund_is_rotation` | Bjorklund's algorithm, as Toussaint describes it, plays the firmware's pattern turned round: for every bar of up to 32 steps and every number of hits, its output is `Euclid.hit` read from some step, checked case by case. | "Euclidean rhythm" usually means Bjorklund's output; the firmware plays the floor-function form instead because a step is then one division, with no list to build. |
| `euclid_major_scale_is_seven_of_twelve` | The major scale is the seven-hit Euclidean pattern on twelve steps, started on its sixth step; the major pentatonic is the five-hit one started on its seventh (both as the SCALE table's masks). | the scales and the rhythms are one construction: the diatonic scale is the maximally even seven of twelve (Clough and Douthett), so the SCALE knob and the HITS knob are reading the same word; a lane set to seven hits in twelve steps taps out the major scale. |
| `notes_start_valid` | A fresh note memory is consistent for any range from 1 to 65535 positions and any loop length from 1 to 16. | the lane starts in a state the algorithms can rely on, whatever the seed. |
| `notes_choose_stays_in_range` | Whichever algorithm picks, the pitch is inside the range and the memory stays consistent. | the note can never land outside the range the lane was given, and no algorithm can corrupt the memory the next pick depends on, however long it runs. |
| `notes_up_visits_every_position` | UP climbs one position a note and wraps at the top, so from position `p` the `i`-th note is at `(p + i) % span`: the first `span` notes visit every position once. | an UP lane is a rising scale that covers its whole range with no position skipped or repeated. |
| `notes_down_visits_every_position` | DOWN falls one position a note and wraps at the bottom: from `p` the `i`-th note is at `(p + (span - 1) * (i + 1)) % span`, so the first `span` notes visit every position once. | a DOWN lane is a falling scale over its whole range with no position skipped or repeated. |
| `notes_bounce_moves_one` | BOUNCE never jumps: each note is at most one position from the last, in a range of at least two. | a BOUNCE lane is a smooth up-and-down line; it can never leap across its range. |
| `notes_walk_bounded` | WALK moves at most `amount` positions a note (the lane draws its step below `2 * amount + 1`, and the position is inside the range). | the AMOUNT knob is a real limit on how far a WALK lane can jump between two notes. |
| `notes_loop_repeats` | LOOP with no mutation plays the same note again every `amount` picks: the memory never changes, and the slot goes round. | MUTATE at zero is an exact loop, the hook a listener can hold on to. |
| `notes_markov_moves_at_most_three` | MARKOV moves at most three positions a note, jump or no jump (the move classes are -3 to +3, and a doubled move is cut to that range). | a markov lane walks; whatever it learnt from the keys or the style says, it never leaps across its range. |
| `notes_grammar_moves_at_most_two` | GRAMMAR moves at most two positions a note: its symbols step or skip, up or down. | the grammar shapes a line of steps and thirds, never a leap, whatever grammar and depth. |
| `notes_learn_keeps_valid` | A key the player presses leaves the memory consistent, for any note: the step sequencer writes it into the range, the markov chain counts it. | nothing you play can corrupt the memory the lane plays from. |
| `notes_turing_locked_repeats` | TURING with FLIP at 0 is a locked loop: after `len` picks the register's `len`-bit window is exactly what it was, so the notes repeat every `len` picks (once the bits above the window, which the first picks still read, have been pushed out). | FLIP at zero is a promise of an exact loop of LENGTH notes, the hook a listener can hold on to; turning FLIP up is the only way the loop changes. |
| `notes_grammar_phrase_never_empty` | A grammar always has a phrase: at every depth it holds at least one symbol. | the GRAMMAR source never falls back to a default symbol; every note it plays comes from the phrase the grammar wrote. |
| `notes_scale_tone_in_scale` | CHORD's tones are notes of the scale: the `n`-th tone above `low` is in the scale whenever the scale has more than `n` notes in the five octaves above `low`. | the CHORD source climbs real scale (or chord) tones, not positions that the snap then has to mend; with chord follow on, those are the chord's notes. |
| `quantizer_snap_keeps_scale_notes` | A note that is already in the scale stays as it is. | quantizing a melody that is already in key changes nothing, so it can be repeated. |
| `quantizer_snap_in_scale` | `snap` gives a note of the scale, as long as the scale has at least one note and the note is at least 6 (so a search 6 semitones down cannot run off the bottom). | the melody can never play a note outside the key you chose. |
| `quantizer_snap_is_near` | `snap` never moves a note more than 6 semitones (same conditions as above). | quantizing keeps the shape of the melody; no note jumps by an octave. |
| `quantizer_snap_monotone` | The quantizer never inverts an interval: of two notes at least 6, the higher never snaps below where the lower snaps, for every non-empty scale. | UP goes up, DOWN goes down and a WALK keeps its direction after the snap to the scale; quantising can merge two notes onto one scale note, but it cannot swap their order and turn a rising line into a falling one. |
| `random_below_lt` | A random pick is always below its limit, so it is a valid index into a list of `limit` choices. | a pick one too big would read past the end of a note list or a step table. |
| `random_never_stands_still` | The generator never stands still: no state maps to itself, so a random lane can never freeze on one value. | whatever the seed, the next draw is a different state, so random, walk and the play chance keep moving; a stuck generator would play one note forever. |
| `harmony_mask_never_empty` | The mask handed to a lane always has at least one note and fits in 12 bits, for every scale, key, progression, chord and follow mode the firmware offers, the Tonnetz walks included. | `lane_note_in_scale` needs a non-empty 12-bit scale; this is what makes that promise hold for the chord-following lanes too, so a chord change can never leave a lane with nothing to play. |
| `harmony_follow_in_key` | On a table progression with chord follow, 7TH or TRIAD, every note a lane may play is a note of the key's scale, whatever chord it is on: the chord is stacked from the key's scale at the chord root, not a shape moved to the root. | a chord progression played with chord follow stays in the key. |
| `harmony_progression_chord_has_root` | With chord follow, 7TH or TRIAD, the chord's root is among the lane's notes, in every scale and key, on the tables and on the walks alike. | joined with `harmony_chord_root_in_key`, a table progression's chord is a chord of the key with its root present, and a walk's chord is the triad the screen names; a lane following either can play the root, not only upper notes of some other chord. |
| `harmony_chord_root_in_key` | On a table progression, every chord root is a note of the key's scale: whatever the scale and chord, the root the lanes move to (and the screen names) is a semitone step that the scale has, below an octave. | progressions are written as degrees, so 1-4-5-1 is I IV V in a major key and i iv v in a minor one; this is the promise that a chord never lands on a note outside the key. |
| `harmony_walk_chord_is_triad` | On a Tonnetz walk (progressions 8 and up) with chord follow, 7TH or TRIAD, a lane plays exactly the walk's triad turned to the key: three notes, and the chord the screen names. | the walks leave the key on purpose, one note at a time (`harmony_walk_keeps_two_notes`); this is the promise that what the lane plays is that triad and nothing else, so the screen's chord name is the truth about the notes. |
| `harmony_walk_keeps_two_notes` | Every move of a Tonnetz walk keeps two of the triad's three notes and changes one: consecutive chords of any walk share exactly two pitch classes. | this is what makes the walks sound like voice leading rather than jumps: P, L and R are the three ways to change one note of a triad and get another triad, so a lane on a walk moves one note at a time, through all 24 triads if the word is L R. |
| `harmony_complement_outside_key` | COMPL (chord follow 3) plays the notes outside the key's scale and nothing else, for every scale and key, whatever chord is on; the chromatic scale, which leaves nothing out, plays whole. | COMPL is a second voice that never collides with a lane in the key, the black keys to its white; with `harmony_complement_interval_content` it has the key's intervals, so it belongs to the same music while sharing no note with it. |
| `harmony_complement_interval_content` | Babbitt's hexachord theorem in its general form, any cycle `Z_n` and any set: the pairs at distance `d` in the complement are the pairs at that distance in the set, plus `n - 2 * size` (an ordered count, each unordered pair seen from both ends). | it is why COMPL sounds like the scale it was cut from: the black keys have the white keys' intervals, two fewer of each, and the whole-tone scale's complement has exactly its own. |
| `harmony_hexachord_theorem` | Babbitt's hexachord theorem on the firmware's own masks: every six-note set of the twelve pitch classes has the interval vector of the six it leaves out, checked for all 4096 masks. | the instance the name comes from, on the 12-bit masks the lanes play from: a hexachord and its complement are indistinguishable by interval content, which is the general theorem above at `n = 12`, `size = 6`, where the difference `n - 2 * size` is zero. |
| `tonnetz_moves_are_involutions` | Each of P, L and R undoes itself: C major to E minor and back. | a walk can always be retraced; and it is the first of the dihedral relations below. |
| `tonnetz_group_has_order_24` | The group the three moves generate has exactly 24 elements: every word of moves acts as one of the 24 listed elements, and no two of those act alike. | however long a word of P, L and R, there are only 24 things it can do to a triad; the knob's walks live in a small, fully known group (the dihedral group of order 24, `tonnetz_group_is_dihedral`), the neo-Riemannian PLR group of music theory. |
| `tonnetz_simply_transitive` | The group acts simply transitively on the triads: from any triad there is exactly one element reaching any other. | every one of the 24 triads is reachable from every other by some word of moves, and the word's effect is determined by where it sends a single triad: a walk that returns C major to C major returns every triad to itself. |
| `tonnetz_commutes_with_transposition_and_inversion` | The PLR group commutes with every transposition and every inversion (the duality of the two groups, Lewin's): moving by P, L or R and then transposing is transposing and then moving, likewise inverting. | a walk sounds the same in every key: the walk from D major is the walk from C major moved up a tone, note for note; and the walk from a minor triad is the inversion of the walk from a major one. |
| `tonnetz_group_is_dihedral` | The dihedral relations: L R has order exactly 12, L has order 2, and L conjugates L R to its inverse R L. | with `tonnetz_group_has_order_24` this names the group: the dihedral group of order 24, the symmetries of a 12-gon, with L R the rotation and L a reflection. |
| `tonnetz_walks_are_cycles` | The L R walk visits all 24 triads, each once, and comes back after 24 moves, from any start; the P L walk is a cycle of six (a hexatonic cycle) and the P R walk one of eight (an octatonic cycle). | the walks on the knob are these: L R is a Hamiltonian cycle on the Tonnetz, every major and minor triad once in 24 chords, a note changing at a time (`harmony_walk_keeps_two_notes`); P L and P R are the two short cycles, six and eight chords, that the same two-note rule allows. |
| `arp_note_is_held` | Every note the arpeggiator starts is a note you are holding, raised by fewer than `octaves` octaves. | the arpeggiator can only play what you play; it never adds a note of its own, whichever mode and however it is set. |
| `arp_make_valid` | A fresh arpeggiator is consistent, for any step. | the arpeggiator starts in a state the rest of the firmware can rely on, whatever the knobs say. |
| `arp_set_valid` | Changing the settings keeps a consistent arpeggiator consistent, whatever numbers are given. | turning the ARP knobs mid-phrase cannot leave a timer or counter out of range. |
| `arp_keys_valid` | Pressing, releasing or clearing keys keeps a consistent arpeggiator consistent. | whatever you play, and however many keys, the held set stays playable and small. |
| `arp_tick_valid` | A tick keeps a consistent arpeggiator consistent. | however long it runs, the counters stay in range and the sounding note and its timer agree. |
| `arp_every_note_on_has_a_note_off` | Every note the arpeggiator starts during a run is stopped: after any sequence of ticks, keys and setting changes, note-ons equal note-offs plus the one note still sounding, which `silence` stops. | letting go of the keys, or stopping, never leaves an arpeggio note hanging. |
| `arp_up_plays_pattern` | UP with a step a tick, from the start of the pattern, plays the pattern through note for note: as many ticks as the pattern has notes start exactly the pattern, in order. | UP is a rising run over exactly what you hold, each note once, in order, before it comes round; the same reading gives every later lap, since the position comes back to the start. |

## System prerequisites

`make install` installs [elan](https://github.com/leanprover/elan) into
`~/.elan` (no sudo) and elan downloads the exact Lean pinned in
`lean-toolchain` (v4.35.0). You need these from your system package manager:

| Need | Why |
| --- | --- |
| `git`, `curl` | elan installer, Lake dependency fetches |
| a C toolchain + libc headers | Lean and the firmware host simulator link native executables |
| `python3` with `venv` | firmware build scripts (Pillow is installed into `.venv`) |
| Linux x86-64 | JieLi's compiler is a Linux x86-64 binary (macOS/Windows: not supported here) |
| `bubblewrap` (Linux only) | sandbox used by `lake comparator` (`make check`) |

Arch / CachyOS: `sudo pacman -S --needed git curl base-devel python bubblewrap`
Debian / Ubuntu: `sudo apt install git curl build-essential python3 python3-venv bubblewrap`
Fedora: `sudo dnf install git curl gcc make python3 bubblewrap`

`bubblewrap` also needs unprivileged user namespaces
(`sysctl kernel.unprivileged_userns_clone` must not be `0`).

## Trusted surface

Proofs cover the Lean code in `Firmware/`. What is proved is listed in `docs/PROOFS.md`; the same statements are
in `Challenge.lean`, and `make comparator` (Lean 4.35's `lake comparator`) checks in a sandbox that `Proofs/`
proves each of them with no axiom but `propext`, `Classical.choice` and `Quot.sound`. `PARANOID=1` also runs
the five external checkers bundled with Lean (leanchecker-paranoid, lean4lean, nanoda, con-leche, con-ron);
all accept. They do not cover:

- `rt/lean_rt.c`: the small Lean runtime (allocator, freeing, arrays, panics). See `docs/LEAN-ON-CHIP.md`.
- Lean's compiler (Lean to C) and JieLi's clang (C to chip code).
- `voices/`: Braids (C++, tables regenerated for 44.1 kHz) and our wrapper. Every engine's sample arithmetic is
  Lean (`Firmware/Analog.lean` to `Macro.lean`), checked sample for sample against the original by `make test-lean`;
  the per-block setup, the delay lines and the glue loops are C and unproved (`docs/LEAN-ENGINES.md`). `make audit`
  checks levels; nobody has listened to it on hardware.
- `fx/delay_glue.c`: the two delay lines and their loop (the arithmetic is Lean, `Firmware/Delay.lean`); not heard.
- `fx/reverb_glue.c`: the reverb's delay memory and the C that moves samples between it and the Lean steps. The
  arithmetic and the order of the steps are Lean (`Reverb.diffuse`, `Reverb.loop` in `Firmware/Reverb.lean`);
  `make test-lean` checks over 20000 samples that the C follows that order, and checks the whole against Clouds'
  original; not heard (`docs/FX.md`).
- `fw/` (Dinghy: platform, drivers, update path) and `fw/firmware/src/dinghy.c`, the C that calls the Lean code.
  Its mix loop (level glide, voice sample, reverb send and return) calls `Firmware/Mix.lean`, which
  `Proofs/Mix.lean` shows never wraps; the master gain and the clip in `fw/firmware/src/platform.c` stay C.
- The hardware, and `web/web_host.c` for the simulator.
- Lean's `Init` library compiled for the chip by `tools/build_lean_init.sh`.

Two checks reach into that list from the proved side:

- **The compiler, checked** (`make test-exports`, `tools/check_exports.py`): every scalar `@[export fm1_*]`
  function (291 of 376; the rest read Braids' tables or take objects) is compiled to C and built for this computer,
  run on random inputs, and Lean's kernel is then asked whether the definition gives the same value
  (`example : f a = c := by decide +kernel`): 1746 values a run, in step on every one. The kernel evaluates the
  definition itself, so this is the compiled code against the thing the theorems are about, with the Lean to C
  compiler, clang and `lean.h` in between. Writing it found one bug: `fm1_harmony_chord_root` reduced its
  arguments after turning them into `Nat`, so a value above 2^31 (which the C never sends) would have reached
  the big-number runtime the chip does not have; it reduces them as 32-bit numbers now.
- **The proofs, watched** (`fw/firmware/src/watch.h`, the simulator page and `make test`): in the simulator and
  host builds, twelve theorems' statements are asserted on the running machine at the point `dinghy.c` consumes
  the Lean's answer: every note a lane starts is in its scale and on a hit, note-ons and note-offs balance, a plain
  lane plays exactly its hits a bar, the mix and the pan stay inside their proved bounds, a swung quarter note is
  24 straight ticks, the chord root is in the key, a saved patch decodes back to its bytes. The theorems are about
  the Lean, so a failure here could only come from the trusted C handing the Lean something a theorem's hypothesis
  excludes, or from the compiled code not being the definition: evidence about exactly the parts the proofs do
  not reach. The simulator shows the counters; `make test` fails on a violation (about 30 million checks over
  the smoke run and the seven demos, none failing).
